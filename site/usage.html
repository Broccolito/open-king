Guide

Commands and options

One invocation reads one PLINK1 fileset and runs one or more analyses over it. This page lists every option the binary accepts, what each one changes, and the parser behaviour that the flag name does not reveal. Every number and every quoted console line below was produced by running the binary.

Synopsis

king -b <fileset>.bed [--fam <path>] [--bim <path>] <analysis>... [parameters...]

Two parts are required. -b names the .bed file; without it the run is fatal at exit status 1 and nothing else happens. At least one analysis flag selects work; with a fileset and no analysis the run loads the data, prints Please specify one of the following 24 options: … and exits 0 having written nothing.

The surface, counted from the binary:

  • 46 long options plus one short option -b (case variant -B), 47 spellings in total.
  • Of the long options, 11 select an analysis, 11 modify one, and 24 are recognised by the parser and then rejected as outside the product scope.
  • 23 distinct output files, plus one transient probe file.
  • All options are matched case-insensitively by unique prefix, so --rel, --RELATED and --related are the same option.

Examples on this page assume king is on the path and that the working directory holds the fileset being named. Analyses are switches, so repeating one turns it back off: --related --related leaves --related off and the run falls through to the "please specify" notice at exit 0 with no files.

Selecting more than one analysis prints a line naming them, and each runs as its own pass. 

$ king -b multifam.bed --kinship --ibs --duplicate
The following analyses will run separately:  --kinship --ibs --duplicate

--cluster suppresses that line entirely, whatever else was requested. It is absent from king -b multifam.bed --kinship --cluster.

Input options

Option Value Default If omitted
-b / -B Required. The .bed file path, not a stem none Fatal: Genotype files are required. e.g., …, exit 1, nothing else runs
--fam <path> String, used verbatim empty Derived from -b by replacing .bed with .fam
--bim <path> String, used verbatim empty Derived from -b by replacing .bed with .bim
--prefix <string> String, concatenated onto every output name king Outputs land in the current directory as king*

There is no --bed. The .bed path is always exactly the -b token.

The -b argument

  • Attached and separate forms are equivalent. -bmultifam.bed and -b multifam.bed both set Binary File : multifam.bed.
  • The option letter is case-insensitive, so -Bmultifam.bed works.
  • The argument must end in a literal lowercase .bed. A stem is not accepted and neither is UPPER.BED.
  • -b followed by a dash-leading token consumes nothing and clears the fileset. king -bmultifam.bed -b --kinship exits 1 with Genotype files are required.
  • Only one fileset per run. A comma in the -b, --fam or --bim value is rejected; see excluded options.

Input probe order

The loader checks the three files in a fixed order. Each failure below was given in isolation, so the first fatal line names the earliest check that the input fails.

Command Exit First fatal line
king -b sub/study.bed --kinship 1 Genotype file sub/study.bed cannot be opened
king -b plain --kinship 1 Please use PLINK binary format as input. (valid bed contents, name has no .bed)
king -b UPPER.BED --kinship 1 Please use PLINK binary format as input.
king -b bad.bed --kinship 1 Please use either PLINK or KING binary format as input. (bad magic)
king -b g.bed --kinship 1 Pedigree file g.fam cannot be opened (no g.fam)
king -b multifam.bed --fam nope.fam --kinship 1 Pedigree file nope.fam cannot be opened
king -b h.bed --kinship 1 Map file h.bim cannot be opened (no h.bim)
king -b multifam.bed --bim nope.bim --kinship 1 Map file nope.bim cannot be opened
king -b multifam.bed --fam short.fam --kinship 1 short.fam: line 1 has 5 fields, expected 6
king -b multifam.bed --fam dup.fam --kinship 1 Please correct problems with pedigree structure, preceded by Family FAM1: Person A_F is duplicated
king -b multifam.bed --bim nochr.bim --kinship 1 No autosome SNPs are available. Please check your map file. (all chr 99)
king -b imajor.bed --kinship 1 Currently only SNP-major mode can be analyzed. (mode byte 0)
king -b trunc.bed --kinship 1 Not enough genotypes at the 999th marker (bed cut to 5000 bytes)
king -b multifam.bed --kinship --prefix nodir/x 1 Cannot open nodir/x$TMP$.ped to write.

The writability probe on --prefix runs after the .fam is opened and before a single pedigree row is parsed. It creates and removes <prefix>$TMP$.ped.

File format requirements

File Requirement
.bed PLINK 1 binary, magic 0x6c 0x1b, SNP-major (mode byte 0x01), at least ceil(N/4) * M genotype bytes
.bim 6 whitespace-separated columns CHR ID CM BP A1 A2
.fam 6 whitespace-separated columns FID IID FA MO SEX PHENO; (FID, IID) unique under ASCII case folding

Two enforced input properties

A1 must be the minor allele. Flipping every homozygote call in multifam.bed produces a fatal: 

$ king -b major.bed --ibs
FATAL ERROR -
Too many first alleles as the major allele (~98.2%). Please use plink1.9 --make-bed to regenerate the genotype data again.

Three analyses are exempt and exit 0 on that same fileset: --kinship, --duplicate and --autoQC. The other eight abort at exit 1: --related, --ibs, --ibdseg, --bysample, --bySNP, --unrelated, --cluster and --build. Some files are written before the abort. --ibs, --related, --bysample, --bySNP, --unrelated, --cluster and --build leave <prefix>allsegs.txt behind; --ibdseg leaves <prefix>allsegs.txt and <prefix>splitped.txt.

The .bim must be sorted by (chromosome, position) ascending for any segment work. An unsorted map is not fatal. The run exits 0, reports the offending pair of markers, and suppresses the segment outputs. 

$ king -b unsortedpos.bed --ibdseg          # exit 0, only kingsplitped.txt written
Positions unsorted: rs1_1009689 at 65904473, rs1_1055261 at 65851170.
  Note chromosomal positions can be sorted conveniently using other tools such as PLINK.

$ king -b unsortedchr.bed --ibdseg          # exit 0, only kingsplitped.txt written
Chromosomes unsorted: rs22_14205438 on chr 22, rs21_1002722 on chr 21.
  Note chromosomal positions can be sorted conveniently using other tools such as PLINK.

Chromosome classification

At --sexchr 23, the default. Numeric codes are re-partitioned by --sexchr; the alphabetic spellings X, Y, XY and MT are classified by name and never move.

Code Class
1..22 Autosome
25, XY Autosome, pooled into the autosome total
23, X X chromosome
24, Y Y chromosome, excluded from relatedness
26, MT Mitochondrial, excluded from relatedness
anything else Dropped at map load, reported as N other SNPs are removed.

The sexchr fileset carries 2000 markers on chr 1, 2000 on chr 2, 1500 on 23, 300 on 24, 150 on 25 and 50 on 26. It loads like this: 

$ king -b sexchr.bed --kinship
  Genotype data consist of 4150 autosome SNPs (including 150 XY SNPs), 1500 X-chromosome SNPs, 300 Y-chromosome SNPs, 50 mitochondrial SNPs
  PLINK maps loaded: 6000 SNPs

The analyses

Eleven analyses are implemented. Each section below gives what the flag computes, the exact output file set with --prefix written as <p> (default king), the parameters that modify it, and a runnable example.

--related

Kinship for every pair, IBD segments for the close ones, and an inferred relationship label. It reports up to degree 1 by default, and it is the only analysis with a non-zero default degree.

File Written when
<p>.kin At least one family has 2 or more members. 16 columns
<p>.kin0 The between-family stage confirms a candidate. At degree 1 or 2 that stage also requires N >= 100. 14 columns
<p>allsegs.txt The map yields at least one usable segment
<p>X.kin The X map yields a usable segment. 9 columns, segment layout, different from --kinship's X.kin
<p>X.kin0 A .kin0 was written and the X map has a usable segment

Modified by --degree, --seglength, --cpus, --prefix and --sexchr. Two size gates apply:

The --kinship test is Kinship >= 2^-(d + 1.5) against the IEEE double, not the printed value. On the same fileset, --ibdseg gives 104 .seg rows with no degree, 43 at degree 1, 68 at degree 2, 88 at degree 3, and 36 at degree -2. Since 68 + 36 = 104, a negative degree reports the complement.

Bare --degree with no value means 1. --degree 3.0 also means 1: the token is rejected as a value, the int toggles from 0 to 1, and 3.0 is reported as ignored.

--noscreen

Accepted, echoed and inert. Running bigish --related --degree 2 with and without --noscreen 1 produces identical md5s for both .kin and .kin0, and the option has no reader outside the parser.

Its default -1717986816 is not a value. In the reference it is uninitialised memory that overlaps --minConc's storage, and open-king reproduces the overlap byte for byte:

The "Options in effect" echo

Every analysis pass opens with an Options in effect: block naming the analysis and a subset of the parameters. The whitelist is --degree, --minConc, --cpus, --prefix, in that order, after the analysis name. --kinship, --related and --ibdseg use narrower lists that omit --minConc. The same command line produces two different blocks depending on which analysis ran: 

$ king -b dups.bed --duplicate --minConc 0.9 --degree 2 --cpus 2 --prefix q_
Options in effect:
	--duplicate
	--degree 2
	--minConc 0.9
	--cpus 2
	--prefix q_

$ king -b multifam.bed --kinship --cpus 3 --degree 2 --minConc 0.9 --prefix ZZ_
Options in effect:
	--kinship
	--degree 2
	--cpus 3
	--prefix ZZ_

This is a stdout-parity detail rather than a defect. Four things are missing from the block by design:

  • --seglength is never echoed, although it changes the output.
  • --minConc is dropped for --kinship, --related and --ibdseg.
  • --degree 0 and --cpus 0 are not echoed, because both are treated as unset.
  • --prefix is echoed only when it differs from king.

A separate block, The following parameters are in effect:, prints on every run before any analysis and is the fastest check that a command line was understood. Its value rendering follows four rules:

Kind Off or unset Set
switch --kinship --kinship [ON]
int Hidden when 0: --degree --degree [2]
double Hidden when 0 and never given: --maxP %.2f, or %.1e when non-zero and below 0.01
string Always shown: --trait [] --prefix [king] 
$ king -b multifam.bed --callrateN 0.9 --callrateM 0 --seglength 0.005 --degree 0 --cpus 4 --prefix p_
              Inference Parameter : --degree, --noscreen [-1717986816],
                                    --seglength [5.0e-03], --minConc [0.80]
                     QC Parameter : --callrateN [0.90], --callrateM [0.00]
              Computing Parameter : --cpus [4]
                 Output Parameter : --prefix [p_], --rpath []

Parser rules

  1. Case-insensitive unique-prefix matching. --rel, --RELATED and --related are the same option. An ambiguous prefix warns and is ignored: --r, --pc and --rp all give Command line parameter --X is ambiguous. A name longer than the option is undefined: --related=1 gives Command line parameter --related=1 is undefined. Neither aborts.
  2. Switches toggle. --related --related leaves --related off, and the run falls through to the "please specify" notice at exit 0 with no files.
  3. A value is consumed only if it looks like one.
    Type With a value token With no value token
    switch Never consumes Toggles
    int Consumes iff ^[+-]?[0-9]+$ Toggles between 0 and 1
    double Consumes iff the first char is [0-9.+-] and any exponent is complete Left unchanged
    string Consumes whatever comes next, option or not Left unchanged

    --degree 3.0 produces --degree [1] plus Command line parameter 3.0 (#5) ignored. --trait --related --kinship sets the trait to the literal --related and leaves --related off, silently.

  4. Everything else is reported as ignored, with a 1-based argument index. king -b multifam.bed --kinship -h foo gives Command line parameter -h (#4) ignored and Command line parameter foo (#5) ignored.
  5. A lone -- borrows the next non-dash token as an option name, and that option never takes a value. king -b multifam.bed -- related gives Options in effect: --related.
  6. The WARNING block starts with a BEL byte (0x07). Read with od -c the sequence is \n \n \n \a W A R N. A grep '^WARNING' will not match; strip control characters first.

Excluded options

24 long options and one input form are recognised by the parser and then rejected before any input file is opened. The banner still prints them, which keeps the parse surface compatible with KING 2.3.2. Every one of them exits 1. The fatal body is:

  • Nothing after the banner runs: no KING starts at, no input probe, no output file.

Diagnostic block shapes

The fatal block, always preceded and followed by a blank line:


FATAL ERROR -
<message>

The warning block, preceded by a 0x07 BEL byte, never aborting:


<BEL>WARNING -
Problems encountered parsing command line:

Command line parameter -h (#4) ignored
Command line parameter foo (#5) ignored

Startup order

  1. Banner and the parameters-in-effect block.
  2. The WARNING block, if any.
  3. FATAL ERROR if no -b was given, and nothing else.
  4. Product-scope rejection of excluded requests.
  5. Either the "please specify one of the following 24 options" notice or the "will run separately" line.
  6. KING starts at <time>.
  7. Parameter checks, in the order --maxP, --sexchr, --seglength, --minConc, --risk/--model.
  8. FATAL ERROR if the .bed cannot be opened.
  9. The analyses.

A completed run closes with KING ends at <time> and a blank line. A no-analysis run and a fatal exit never print it. king -b multifam.bed ends at KING format genotype data successfully converted. and writes no files.
