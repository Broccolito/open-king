Verification

Parity

Parity here means one operation: replay a captured KING invocation with open-king and compare the result byte for byte. This page gives the measured numbers, names every difference that is known and unfixed, and states where the evidence stops.

The measured result

Captured invocations replayed 480
Cases passing 480 PASS, 0 FAIL
Output files byte-compared 876
Files diff-excluded 8
Regression baseline MATCH, 480 cases
cargo test --workspace 355 passed, 0 failed

A case passes only when the exit status, the standard output, the standard error, the set of files produced and the bytes of every file all match. The eight exclusions are all the same file, <prefix>X.kin0, on the captures taken without --cpus 1. The reason is a race in the reference, described below. One timing probe in the Rust suite is marked ignored.

Scope of every number on this page

All of it is measured against one KING build: KING 2.3.2, Mach-O 64-bit arm64, on macOS. No cross-build or cross-platform differential has been run. See One reference build, one host, which states the consequences rather than softening them.

What is compared

Each directory under tests/parity/golden/<group>/<case>/ is one captured reference invocation. It holds cmd.txt (the argv, with {KING}, {DATA} and {ALT} placeholders), exitcode.txt, stdout.txt and stderr.txt verbatim, and every output file the reference wrote into its working directory.

run_parity.py replays cmd.txt with the open-king binary in a fresh temporary directory and compares five things: exit status, standard output, standard error, the set of files produced, and the bytes of every file. A file the reference did not write is a failure, and so is a missing one.

490 invocations are captured and 480 are replayed. The ten under core/_analysis/ are alternate-parameter captures kept for analysis and are included only with --include-analysis.

The five normalized lines

Five kinds of line are genuinely not reproducible. They are normalized on both sides before comparison, never on open-king's side alone.

  • Timestamps, on every … starts at and … ends at line.
  • Thread counts, in N CPU cores are used, which follows the host.
  • Progress tokens, the carriage-return separated 10%20%… sequences, whose granularity follows timing.
  • Absolute input paths, which the reference echoes back for the .bed, .bim and .fam it was given.
  • The --noscreen [<int>] value, which is uninitialised memory in the reference's own banner. Across the 484 captured stdouts that print it, it takes three values: -1717986816 469 times, -858993408 14 times and -515396096 once.

One file is excluded from diffing entirely. The reference's between-family X-chromosome writer is not serialised: six identical invocations of king -b sexchr.bed --kinship produce six different files, and one sampling caught the writer mid-truncation, with records torn mid-field and identifier columns from different pairs interleaved. Adding --cpus 1 makes it deterministic, so no capture made without it can be a golden. <prefix>X.kin0 is therefore excluded on 8 of the 13 cases that produce it, which is the whole of the "8 diff-excluded" figure. The other 5, all captured with --cpus 1, are diffed and are byte-identical.

Nothing else is normalized. Row order is compared, not sorted. Trailing whitespace is compared. Column widths are compared. Two of the rules open-king implements were found only because the comparison is a byte diff: the row order of <prefix>.seg, and the fact that its PropIBD column is computed differently from the identically named column in <prefix>.kin. Every row-level grader in the project matches rows on their identifier columns before comparing, and had reported 0 extra and 0 missing rows on a file whose rows were in the wrong order for the entire life of the project. 486 of the goldens contain bare carriage returns, so .gitattributes marks the golden tree, the baseline and the fixture caches -text to stop a platform's git rewriting them on checkout.

The runner checks itself

Running the same suite with the reference binary as the implementation gives 480 PASS, 0 FAIL with 876 files byte-compared. That is the evidence that the normalization above is not hiding a real difference: the reference agrees with its own captures under exactly the rules open-king is held to.

The regression baseline

tests/parity/BASELINE.txt records the outcome of all 480 cases with their per-file notes. run_parity.py --baseline fails on any difference in either direction: a new failure, a changed reason for an existing failure, or an unrecorded improvement. The last of those is deliberate, so that a change which fixes a case must also update the file that said it was broken. CI runs it on every push.

The corpus

The captures come from 13 simulated PLINK1 filesets: trio, nuclear, threegen, multifam, dups, missing, monomorphic, sexchr, unrelated, admixed, singleton, pair and bigish. The largest, bigish, has 200 samples; multifam has 20 and threegen 12. Nine of the thirteen have 16 samples or fewer.

What the small filesets do not prove

nuclear (6 samples, 10,000 markers), missing (6, 10,000), sexchr (10, 6,000) and monomorphic (12, 5,000) each report the same 14 .seg rows: the within-family pairs of one six-person nuclear family. Half of monomorphic's markers carry no usable information. On these the reference's own segment numbers are nowhere near the pedigree the generator built, so agreeing with the reference there says little about the segment caller.

The limit of a saturated corpus

<prefix>.seg is byte-identical in all 50 captures, on all 4,172 rows, at the default reporting floor and at --seglength 5 and --seglength 10 alike. The primary --ibdseg scorecard is 982 of 982 rows exact at each of the three floors, with 0 extra and 0 missing pairs. That is a statement about 480 captures of 13 simulated datasets. It is not a proof that the segment caller is right in general, and the corpus can no longer tell the difference: it has stopped grading the caller and become a regression guard. The measurement that still discriminates is the out-of-sample battery below, and it is not clean.

Five held-out differences

The one retained safety divergence

Because the corpus is saturated on the segment columns, the same binary is also graded on filesets it has never seen. oosseg.py builds 24 of them with the corpus generator's own simulator on 8 seeds used nowhere else in the repository, in three pedigree shapes, runs both binaries at 3, 5 and 10 Mb, and diffs <prefix>.seg byte for byte. 

72 runs, 6 713 reference rows   ->   68 byte-identical
rows: 0 extra, 0 missing, 4 value-differing

That is 94.4 % of whole-file runs and 99.94 % of rows. The four differing rows have one shape: a single full-sib pair on two filesets with exactly 40,000 markers, at the 3 and 5 Mb floors. IBD1Seg is exact; open-king's IBD2Seg is lower by 0.0181 to 0.0182, and PropIBD follows it.

Two controls make the cause precise. Holding the same seeds, genotypes and target pair, the output is exact at 39,999 markers and exact after appending one all-missing marker to reach 40,001. Only 40,000 differs. On an array whose length is an exact multiple of 64, the reference reads past the end of the marker array: it adds an absolute coordinate, the last marker's position, rather than a difference, to a pair's IBD2 total, so IBD2Seg can come out larger than 1. The behaviour was swept at 320, 384 and 448 markers, where it appears on some pairs and always as exactly that added position over the usable total, and at 319, 321, 383, 385 and 449, where it appears on no pair at any seed. It shows identically in X.kin and X.seg, so it is in the shared caller.

This is a memory-safety bug in the reference, not a caller rule, and safe Rust does not emulate it. The divergence is retained on purpose and asserted by tests/parity/probes/segment_residuals.py::check_safe_tail_divergence, which runs all twelve controls. It is not open work and is not part of issue #11. Every corpus array ends mid-word, so the corpus cannot reach it at all: 0 corpus rows are affected.

An independently compiled reference

The goldens are only as good as the binary that produced them. To test that, KING 2.3.2 was compiled independently from the published source with a different compiler, Homebrew GCC 16 on arm64, and all 480 captured invocations were replayed against that build.

Every one of the 876 output files was byte-identical to the golden capture. The only differences were on standard output, on two lines: the uninitialised value in KING's own banner, which differs between compilations, and the reported CPU core count. On the stdout comparison alone, 475 of the 480 cases were marked FAIL, with zero output-file differences. Those two lines are the same ones the replay normalization targets, so the recorded failures show that the normalization did not absorb the cross-build form of them.

Widening the replay past the 480 graded cases to all 490 captured invocations finds one behavioural difference between the two builds, and it lands on the one option whose value was never initialised. On --related --degree 1 --noscreen over multifam, the second build bypasses the screen and writes a king.kin0 holding eight between-family pairs. The binary the goldens were captured from writes no such file and reports No close relatives are inferred. open-king matches the capture binary.

That is one fact rather than two. --noscreen takes an integer, and the integer it carries is uninitialised memory overlapping --minConc's storage. An undefined value reaching a branch is how one source yields two behaviours. So open-king treating --noscreen as inert is a deliberate match to the capture binary and not a gap: no implementation satisfies both builds, because the reference does not agree with itself. The remaining difference across those 490 cases is X.kin0 on sexchr, which is KING's own race between threads and differs between two runs of one binary.

What that supports: KING's computed output is reproducible across independent builds of the same source, while its banner and its one uninitialised option are not. The goldens this project is graded against are a property of the program rather than of one compiler's code generation. What it does not support: anything about a different KING version, or about a different platform. Same source, same version, same architecture, different compiler is one axis of three.

Analyses deliberately not implemented

open-king is the smallest useful permissively licensed implementation of KING's relatedness workflow. It is not intended to reproduce every analysis that accumulated in the original executable. The following are outside the product boundary and are not planned for this package.

  • Population structure: --pca, --mds.
  • Runs of homozygosity: --roh.
  • GRM, association and risk analysis: --makeGRM, --lmm, --tdt, --gdt, --risk.
  • PLINK-export orchestration: --plink.
  • R-based plotting: --rplot, --pngplot, --rpath.
  • KING's comma-separated multi-fileset merge mode.

Their spellings remain in the parser and the banner so that KING 2.3.2's command-line surface stays recognisable. Asking for an excluded analysis, its associated parameter, or comma-separated input is a fatal error with exit status 1 before any input file is opened, so a requested workflow cannot appear to succeed without producing its promised output. These are product boundaries. They must not be counted as relatedness-parity failures, and expanding the boundary later would require an explicit scope decision, clean-room behavioural evidence and its own tests.

One computing-scope note. --cpus <n> is accepted, echoed and used in compatibility console text, but it does not currently promise a strict Rayon worker-thread cap. Computed files are deterministic across thread counts, and exact performance parity with KING is not a product goal. Separately, <prefix>.segments.gz is documented in KING's manual, but the 2.3.2 build ships without zlib in its segment writer and writes no such file on any invocation in the corpus, so it is not a parity target.

One reference build, one host

The standing caveat

Every figure on this page was measured against one binary: KING 2.3.2 - (c) 2010-2023 Wei-Min Chen, Mach-O 64-bit arm64, run on macOS Darwin 25.5.0, Apple silicon. No cross-build or cross-platform differential has been run. That is a gap in the evidence, stated as one, not a claim that no such differences exist.

The caveat bites hardest on the segment engine, because KING's segment numerics are not stable across KING's own releases, on KING's own account. The version history records 2.1.2 "IBD segment algorithm improved"; 2.1.3 "--ibdseg, --related, --roh algorithms improved"; 2.1.4 up-to-4th-degree inference for --related and --ibdseg; 2.2.1 a maxIBD1/maxIBD2 fix; 2.2.5 "--ibdseg is substantially improved"; and 2.2.7 the 2.2.5 --ibdseg bug "completly fixed" [sic]. The algorithm behind those changes has never been published.

So "byte-identical to KING" on this page means byte-identical to 2.3.2. open-king is not claimed to reproduce 2.1.x, 2.2.x, or whatever follows 2.3.2, and against those builds the .seg columns should be expected to differ. Anyone comparing against a different KING should re-capture the goldens before believing any segment number here.

The rest of the surface is far less exposed. The kinship and IBS estimators are published, in Manichaikul et al. 2010, and the file formats are stable. It is the unpublished segment caller, and only it, whose parity is pinned to a single build. The rebuild described above addresses the compiler axis and leaves the version and platform axes open.

Reproducing these numbers

run_parity.py and measure_gaps.py use the Python 3 standard library only, regenerate the input corpus automatically on first run (about 20 s), and need no reference binary. Start from a checkout. 

cd /path/to/open-king
cargo build --release

These four need nothing but the open-king build.

python3 tests/parity/run_parity.py --impl ./target/release/king
python3 tests/parity/run_parity.py --impl ./target/release/king --baseline
python3 tests/parity/measure_gaps.py --impl ./target/release/king -q
cargo test --workspace

These three drive a KING 2.3.2 binary directly, so they need one on the machine. 

python3 tests/parity/run_parity.py --impl "/path/to/reference/king"
python3 docs/research/fixtures/oosseg.py --ref "/path/to/reference/king"
python3 tests/parity/probes/segment_residuals.py \
    --ref "/path/to/reference/king" --impl target/release/king

run_parity.py exits 0 when every case passed, 1 when at least one failed, and 2 on an internal error. With --baseline it exits 0 only when the outcome matches tests/parity/BASELINE.txt exactly. A clean checkout reproduces the same counts: a pristine copy of the tree builds in 9.5 s from cold and its binary gives 480 PASS, 0 FAIL with baseline: MATCH, so the published figures do not depend on a warm target/ or a pre-generated corpus.
