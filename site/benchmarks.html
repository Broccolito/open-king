Verification

Benchmarks

The same analyses, the same inputs, one machine, both programs. Two things came out of it: the counting analyses cost about what KING costs, and everything that builds IBD segments costs far more and gets worse as the cohort grows.

The result in two sentences

On the golden corpus, which is small, open-king finishes first in 72 of 80 cells, because at that size the run is mostly process startup. On a cohort of a few hundred samples that stops being true: --kinship and --ibs stay level with KING on CPU work, while --related, --ibdseg, --unrelated, --cluster and --build take between 5 and 55 times more CPU, and the gap widens with every doubling of the sample count.

Output does not change with any of this. Across the whole matrix, 206 of 217 output files were byte-identical to KING's. The 11 that were not are listed under output agreement, and none of them is on a corpus dataset.

Read CPU seconds, not wall seconds, when the two disagree

The machine was not idle. Wall times are therefore an upper bound, and cpu/wall is pushed down by descheduling rather than by anything about the binaries. CPU seconds count work done rather than time elapsed, so they survive the contention. Every cell faced the same conditions, so wall times remain comparable with each other.

The reference binary

KING publishes a precompiled macOS binary. It is x86_64, and it does not launch on an arm64 host: it asks for libgomp.1.dylib from an Intel Homebrew GCC 9 that is not there. Running it under translation would have meant timing an emulated program against a native one, so KING 2.3.2 was compiled from the published source instead, with g++-16 -lm -lz -O2 -fopenmp, giving a native arm64 binary. Both programs therefore run on the same instruction set.

The source was compiled and then deleted without being read, so open-king's clean-room rule is intact. That rebuild is not byte-equal to the binary the parity goldens were captured from, and the parity page measures exactly how far apart the two builds are.

The split falls exactly where the segment engine starts. Analyses that only count genotype pairs match KING. Analyses that build IBD segments or run the relatedness screen do not. This is tracked as issue 12, with the hypothesis that KING prunes the pair set before the expensive per-pair work.

How the gap grows

--unrelated, markers held at 100,000, sample count doubling. Wall time, median of five.

A constant factor would be a footnote. This is not a constant factor: the ratio is 12x at 200 samples, 34x at 400 and 116x at 800. Extrapolating the same curve puts a few thousand samples in the tens of minutes for open-king against seconds for KING. For a cohort of that size, the difference decides whether the program is usable.

Threads are a second, separate gap

--kinship is the clearest case, because the CPU work is level. KING still finishes it in less than half the wall time, by keeping more cores busy.

Cores busy is CPU seconds divided by wall seconds. A value near 1 means the analysis ran serially. So there are two independent things to improve: how much work is done, and how much of it happens at once.

KING obeys the flag: its cores busy falls to 1.00 at --cpus 1. open-king barely moves, 1.64 to 1.58, which is what the option reference and SCOPE.md already say: --cpus is accepted and echoed and is not a strict worker cap. Computed files are the same at every thread count.

Small inputs measure startup, not algorithms

On the ten corpus datasets, the largest of which is 200 samples by 50,000 markers, open-king is faster in 72 of 80 cells, median 3.7x. On trio, three samples, it is 0.004 s against 0.020 s.

That number is real and it is nearly meaningless. At that size both programs spend most of their time starting up, and open-king starts faster. It says nothing about how either program behaves on a study-sized cohort, which is why the large filesets exist.

Memory

Peak resident set size across the whole matrix: open-king 3.7 MB to 113.2 MB, KING 8.6 MB to 68.5 MB. open-king holds more of the fileset in memory, and the widest gap is on --kinship, where it peaks at 3.8 times KING on 200 samples and 2.9 times on 800. Both remain small enough that memory is not the constraint on any machine that would run this work.

The full account, with the determinism control, is in issue 11.

What this does not measure

  • One host, one architecture, one reference build. No cross-platform comparison was run.
  • A loaded machine. CPU seconds survive that; wall times are an upper bound.
  • Filesets in which no sample declares a parent. That is the shape a cryptic-relatedness study has, and it is also the shape that puts the most work through reconstruction. A cohort with declared families may look different.
  • Disk. Every input was on local SSD and already in the page cache after the warmup run.

Reproducing these numbers

The benchmark script takes both binaries and writes the full matrix, the per-file sha256 comparison and the thread calibration. 

python3 benchmarks/run_benchmark.py \
  --binary-b /path/to/king-2.3.2 \
  --label-b "KING 2.3.2" \
  --reps 5

Results land in benchmarks/results/ as both JSON and Markdown. The synthetic filesets are rebuilt from a recorded seed and are not committed, so a rerun regenerates the same inputs.
