Overview

open-king

open-king estimates how every pair of samples in a PLINK1 fileset is related. It is a clean-room, MIT-licensed Rust reimplementation of the relatedness and quality-control workflows in KING 2.3.2, and on its supported surface it aims for the same command line, the same PLINK1 input and byte-identical output files.

What it does

Given a .bed, .bim and .fam trio, open-king reports a kinship coefficient for every pair of samples, identifies duplicate and monozygotic pairs, infers identity-by-descent segments, and assigns a relationship label to each pair. Around that it produces per-sample, per-marker and automatic quality-control reports, unrelated-sample selection, family clustering and pedigree reconstruction. Results are written as plain text files, using the file names, columns and row order the reference program uses. The same engine is available as a Rust library, king-core, which returns owned data rather than a report to parse.

Provenance and license

open-king is not affiliated with, endorsed by, or derived from the source code of the original KING program by Wei-Min Chen and colleagues. It was written from the published algorithm descriptions, the publicly documented file formats, and black-box observation of the reference binary. No KING source code was read or copied.

open-king's own code is MIT licensed. That covers this code only and makes no claim about the original KING, which its authors license separately.

Credit for KING itself belongs to Wei-Min Chen and colleagues at the University of Virginia, whose program kingrelatedness.com this project reimplements and measures itself against.

Quick start

A Rust toolchain (1.75 or newer) is the only requirement to build. Python 3, standard library only, runs the test corpus generator used below. 

git clone https://github.com/Broccolito/open-king
cd open-king
cargo build --release

The binary lands at target/release/king. A run needs a PLINK1 fileset. If you do not have one to hand, the repository can synthesise thirteen of them with no external tools: 

python3 tests/parity/generate_corpus.py --outdir /tmp/kingdocs

Then find the relatives, out to second degree:

target/release/king -b /tmp/kingdocs/bigish.bed --related --degree 2 --prefix demo

The run echoes the options in effect and names each file as it writes it.

That leaves three files: demo.kin with 573 within-family pairs, demo.kin0 with the 26 cross-family pairs that cleared the second-degree cut, and demoallsegs.txt with the usable-genome denominator.

FID1	ID1	FID2	ID2	N_SNP	HetHet	IBS0	HetConc	HomIBS0	Kinship	IBD1Seg	IBD2Seg	PropIBD	InfType
BF01	B01_F	BF02	B02_F	50000	0.2274	0.0132	0.4855	0.1175	0.2885	0.4575	0.3676	0.5964	FS

B01_F and B02_F are declared in different families and share half their genome, with a quarter of it doubled: full siblings the pedigree never mentioned. That is the finding --related exists to produce.

Two things to know first

--prefix is concatenated, not joined, so --prefix demo gives demo.kin and demoallsegs.txt.

On a cohort of any size, pass --degree. Unfiltered, .kin0 is every pair in the dataset.

The analyses

One or more of these must be given, or nothing is computed. Each flag links to its entry on the commands page, which covers every option and the parser behaviour that is not obvious from the flag name.

Flag What it does Writes
--kinship Kinship for every pair, with no segments and no labels .kin, .kin0, X.kin, X.kin0
--related Kinship plus IBD segments and a relationship label per pair .kin, .kin0, X.kin, allsegs.txt
--duplicate Duplicate and monozygotic pairs by heterozygote concordance .con
--ibdseg Pairwise IBD-segment inference on its own .seg, X.seg, allsegs.txt, splitped.txt
--ibs Full IBS and concordance counts for every pair .ibs, .ibs0, allsegs.txt
--unrelated A maximal mutually unrelated subset, and its complement unrelated.txt, unrelated_toberemoved.txt
--cluster Merges families connected by inferred relatedness cluster.kin, updateids.txt
--build Reconstructs pedigrees from the genotypes updateparents.txt, updateids.txt, build.log
--bysample Per-sample QC: call rate, heterozygosity, Mendelian errors bySample.txt
--bySNP Per-marker QC: frequency, genotype counts, error rates bySNP.txt
--autoQC The packaged call-rate and sex QC pipeline four _autoQC_* reports

The common modifiers are --degree, --prefix, --seglength, --minConc and --cpus. --cpus is accepted and echoed in the console text, but it does not promise a strict worker-thread cap. Computed files are deterministic across thread counts.

Out of scope

open-king is the smallest useful implementation of KING's relatedness workflow. It does not reproduce every analysis that accumulated in the original executable. Population structure (--pca, --mds), runs of homozygosity (--roh), GRM, association and risk analysis (--makeGRM, --lmm, --tdt, --gdt, --risk), PLINK-export orchestration (--plink), R-based plotting (--rplot, --pngplot, --rpath) and KING's comma-separated multi-fileset merge mode are not planned for this package.

Their spellings stay in the parser and the banner, so KING 2.3.2's command-line surface remains recognisable. Requesting one of them is a fatal error with exit status 1 before any input file is opened, which stops a requested workflow from appearing to succeed without producing its output. These are product boundaries rather than defects in the relatedness core, and they do not count as parity failures. Use a dedicated tool for those workflows, before or after open-king.

Measured parity

All 480 captured reference invocations are byte-identical: every output file, plus stdout, stderr and exit status.

Measurement Result
Captured invocations 480 PASS, 0 FAIL, 480 total
Output files byte-compared 876, with 8 diff-excluded
Regression baseline baseline: MATCH
Rust tests 355 passing

The eight excluded files are documented, their reference bytes are host-unstable, and they are excluded symmetrically from both sides of the comparison. Every number above is measured against one reference build: KING 2.3.2, Mach-O arm64, macOS. KING's segment algorithm is unpublished and its release notes record repeated changes across 2.1.x to 2.2.x, so byte-identical means to 2.3.2.

Differences the 480-case corpus cannot exercise cost no case but remain part of the claim. The parity page names them and gives the per-analysis breakdown.
