Overview

open-king

open-king estimates how every pair of samples in a PLINK1 fileset is related. It is a clean-room, MIT-licensed Rust reimplementation of the relatedness and quality-control workflows in KING 2.3.2. On its supported surface it takes the same command line and the same PLINK1 input, and writes byte-identical output files: all 480 captured reference invocations match.

What it does

Given a .bed, .bim and .fam trio, open-king reports a kinship coefficient for every pair of samples, identifies duplicate and monozygotic pairs, infers identity-by-descent segments, and assigns a relationship label to each pair. Around that it produces per-sample, per-marker and automatic quality-control reports, unrelated-sample selection, family clustering and pedigree reconstruction. Results are written as plain text files, using the file names, columns and row order the reference program uses. The same engine is available as a Rust library, open-king-core, which returns owned data rather than a report to parse.

Why open-king

On its supported surface open-king computes KING 2.3.2's results and writes them byte for byte, across all 480 captured invocations. The choice between the two therefore turns on the license, what has to be installed, whether two runs of one command agree, and what a run costs. Where the numbers do differ is measured and listed on the parity page.

Property Measured
License MIT. open-king can be vendored, put in a container, packaged by a distribution, shipped inside a product, or forked. KING's terms are "Feel free to use KING for your research, but please do not redistribute AND make profits".
Deployment One file, no runtime dependencies. The macOS binary is 1.1 MB and links exactly one library, /usr/lib/libSystem.B.dylib. Prebuilt binaries ship for four platforms, the two macOS ones notarized by Apple. KING's published macOS binary links libstdc++, libgomp and libgcc_s from a Homebrew GCC 9 under /usr/local, and on Apple silicon it fails to launch with Library not loaded: /usr/local/opt/gcc/lib/gcc/9/libgomp.1.dylib.
Determinism Twelve identical runs writing X.kin0: open-king produced 1 distinct checksum, KING produced 2. KING appends from several threads to one unlocked file handle.
Memory safety Safe Rust does not read uninitialized memory. KING does, in three measured places: its startup banner, the tail of a marker array whose length is an exact multiple of 64, and the value carried by --noscreen, whose effect therefore differs between two builds of the same KING source. The controls that isolate each one are on the parity page.
Speed Faster on wall time in 72 of the 80 corpus cells, median 3.7x. Adding the 24 synthetic cells at 200 to 800 samples, where it is slower on wall time in every one, makes that 72 of 104 and median 3.5x. A trio takes 0.004 s against 0.015 s. On 800 samples and 100,000 markers the two counting analyses are level on CPU work: --kinship 1.43 CPU seconds against 1.53, --ibs 1.77 against 1.95. The other six cost 5x to 55x more CPU at that size, and the gap grows with sample count: --duplicate 1.29 CPU seconds against 0.25, --ibdseg 5.13 against 0.74, --unrelated 19.92 against 0.36, with --related, --build and --cluster between them. That is tracked as issue #12 and reported in full on the benchmarks page.
Peak memory Resident set on a trio: 3.8 MB against 8.6 MB.

Every figure above was measured on one host against one reference build: KING 2.3.2, Mach-O arm64, macOS. Behind the parity claim are 355 Rust tests and a committed 480-case differential suite that needs no reference binary, runs in about two seconds, and runs in CI on Linux, macOS and Windows on every push, so the comparison can be repeated rather than taken on trust.

It was written from the published algorithm descriptions, the publicly documented file formats, and black-box observation of the reference binary. No KING source code was read or copied.

Quick start

Each release is a zip holding one file, the executable. The two macOS builds are signed with a Developer ID certificate and notarized by Apple, so they run out of the archive with no Gatekeeper warning: 

curl -LO https://github.com/Broccolito/open-king/releases/download/v0.1.1/open-king-macos-arm64.zip
unzip open-king-macos-arm64.zip
./open-king

Apple staples a notarization ticket to app bundles, disk images and installer packages, not to a bare command-line executable, so the first run checks with Apple online. The install page has the other three platforms and the checksums.

The walkthrough below builds from source instead, because the test corpus generator it uses ships with the repository. A Rust toolchain (1.75 or newer) is the only requirement to build. Python 3, standard library only, runs the generator. 

git clone https://github.com/Broccolito/open-king
cd open-king
cargo build --release

The binary lands at target/release/open-king. A run needs a PLINK1 fileset. If you do not have one to hand, the repository can synthesise thirteen of them with no external tools: 

python3 tests/parity/generate_corpus.py --outdir /tmp/kingdocs

Then find the relatives, out to second degree:

target/release/open-king -b /tmp/kingdocs/bigish.bed --related --degree 2 --prefix demo

The run echoes the options in effect and names each file as it writes it.

That leaves three files: demo.kin with 573 within-family pairs, demo.kin0 with the 26 cross-family pairs that cleared the second-degree cut, and demoallsegs.txt with the usable-genome denominator.

B01_F and B02_F are declared in different families and share half their genome, with a quarter of it doubled: full siblings the pedigree never mentioned. That is the finding --related exists to produce.

Two things to know first

--prefix is concatenated, not joined, so --prefix demo gives demo.kin and demoallsegs.txt.

--degree is what bounds --kinship. Without it, .kin0 holds every between-family pair, which on this 200-sample fileset is 19,327 rows against 24 at --degree 2. --related runs the other way and defaults to first degree, so leaving --degree off narrows its .kin0 to 3 rows rather than widening it.

The analyses

One or more of these must be given, or nothing is computed. Each flag links to its entry on the commands page, which covers every option and the parser behaviour that is not obvious from the flag name.

Flag What it does Writes
--kinship Kinship for every pair, with no segments and no labels .kin, .kin0, X.kin, X.kin0
--related Kinship plus IBD segments and a relationship label per pair .kin, .kin0, X.kin, X.kin0, allsegs.txt
--duplicate Duplicate and monozygotic pairs by heterozygote concordance .con
--ibdseg Pairwise IBD-segment inference on its own .seg, X.seg, allsegs.txt, splitped.txt
--ibs Full IBS and concordance counts for every pair .ibs, .ibs0, allsegs.txt
--unrelated A maximal mutually unrelated subset, and its complement unrelated.txt, unrelated_toberemoved.txt, allsegs.txt
--cluster Merges families connected by inferred relatedness cluster.kin, updateids.txt, allsegs.txt
--build Reconstructs pedigrees from the genotypes updateparents.txt, updateids.txt, build.log, allsegs.txt
--bysample Per-sample QC: call rate, heterozygosity, Mendelian errors bySample.txt, allsegs.txt
--bySNP Per-marker QC: frequency, genotype counts, error rates bySNP.txt, allsegs.txt
--autoQC The packaged call-rate and sex QC pipeline four _autoQC_* reports

The Writes column is what an analysis can produce, not what every run leaves behind. Which files appear depends on the data: the X files need X-chromosome markers in the map, .kin0 needs a between-family pair, and --duplicate writes a header-only .con when no pair clears the concordance cut below 100 samples, and no .con at all at 100 samples or more. On the 200-sample bigish.bed, --kinship writes two of its four files and --autoQC three of its four; on sexchr.bed both write the full set. The condition for each file is on the outputs page, under Empty, header-only, absent.

The common modifiers are --degree, --prefix, --seglength, --minConc and --cpus. --cpus is accepted and echoed in the console text, but it does not promise a strict worker-thread cap. Computed files are deterministic across thread counts.

Out of scope

open-king is the smallest useful implementation of KING's relatedness workflow. It does not reproduce every analysis that accumulated in the original executable. Population structure (--pca, --mds), runs of homozygosity (--roh), GRM, association and risk analysis (--makeGRM, --lmm, --tdt, --gdt, --risk), PLINK-export orchestration (--plink), R-based plotting (--rplot, --pngplot, --rpath) and KING's comma-separated multi-fileset merge mode are not planned for this package.

Their spellings stay in the parser and the banner, so KING 2.3.2's command-line surface remains recognisable. Requesting one of them is a fatal error with exit status 1 before any input file is opened, which stops a requested workflow from appearing to succeed without producing its output. These are product boundaries rather than defects in the relatedness core, and they do not count as parity failures. Use a dedicated tool for those workflows, before or after open-king.

Measured parity

All 480 captured reference invocations match: every output file byte for byte, plus exit status, plus stdout and stderr once five lines that cannot be reproduced are normalised on both sides. Those five, and why each one is unreproducible, are listed on the parity page.

Measurement Result
Captured invocations 480 PASS, 0 FAIL, 480 total
Output files byte-compared 876, with 8 diff-excluded
Regression baseline baseline: MATCH
Rust tests 355 passing

The eight excluded files are documented, their reference bytes are host-unstable, and they are excluded symmetrically from both sides of the comparison. Every number above is measured against one reference build: KING 2.3.2, Mach-O arm64, macOS. KING's segment algorithm is unpublished and its release notes record repeated changes across 2.1.x to 2.2.x, so byte-identical means to 2.3.2.

Some differences fall outside what the 480-case corpus exercises. They cost no case, and they are still part of the claim. The parity page names them and gives the per-analysis breakdown.
