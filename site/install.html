Guide

Install

open-king is a single self-contained executable. It has no runtime dependencies, reads no configuration files, opens no network sockets, and reads nothing from stdin. Installing it means putting one file on disk.

There are two paths. Download a prebuilt archive from the GitHub release, or build from source. Both end at the same binary. The version documented here is v0.1.1, from the repository Broccolito/open-king.

The macOS build is 1.1 MB and links one library, /usr/lib/libSystem.B.dylib. Nothing else has to be installed first on any of the four platforms.

Requirements

A prebuilt archive needs nothing installed. The requirements below apply to building from source and to running the test suites.

Requirement Value Needed for
Rust 1.75 minimum Building from source. The floor is rust-version = "1.75" in [workspace.package] in the root Cargo.toml.
Rust used by CI current stable The release workflow pins dtolnay/rust-toolchain@stable in .github/workflows/release.yml.
Python 3, standard library only The corpus generator and the parity suite. Not needed for the build.

There is no rust-toolchain.toml in the repository, so rustup uses your default toolchain. Anything at or above 1.75 builds. This tree was checked with rustc 1.92.0.

Download a release build

The repository is public, so the release assets are fetched with an ordinary unauthenticated request. Each archive is a zip holding exactly one file, the executable: unzip it and run it. SHA256SUMS.txt is published beside the archives, so a download can be checked before it is run.

Release assets

Asset Platform Contains
open-king-macos-arm64.zip macOS, Apple silicon open-king
open-king-macos-x86_64.zip macOS, Intel open-king
open-king-linux-x86_64.zip Linux x86_64 (gnu) open-king
open-king-windows-x86_64.zip Windows x86_64 (msvc) open-king.exe
SHA256SUMS.txt all one sha256  filename line per archive

Each archive is packaged in the release workflow from a directory holding the executable alone, with zip -q -X on macOS and Linux and Compress-Archive on Windows. There is no top-level folder to descend into and nothing else to tidy up afterwards. The file inside carries no version number, so the archive name is the only place the version appears. The MIT licence and the README travel with the repository and the release page rather than inside every archive.

SHA256SUMS.txt is produced in the same workflow by sha256sum over the four archives, one line each, and is attached to the release beside them. Check a download against it before running it.

Keep --ignore-missing

SHA256SUMS.txt has four lines, one per archive, and you downloaded one of them. Without --ignore-missing, shasum -a 256 -c SHA256SUMS.txt exits 1 and prints FAILED open or read for the three files you did not download. Measured. The single-file form works too: grep 'open-king-macos-arm64.zip' SHA256SUMS.txt | shasum -a 256 -c -.

macOS, Apple silicon (arm64)

mkdir -p ~/open-king-dl && cd ~/open-king-dl
BASE=https://github.com/Broccolito/open-king/releases/download/v0.1.1

curl -LO "$BASE/open-king-macos-arm64.zip"
curl -LO "$BASE/SHA256SUMS.txt"

shasum -a 256 -c SHA256SUMS.txt --ignore-missing   # open-king-macos-arm64.zip: OK

unzip open-king-macos-arm64.zip                    # open-king
./open-king                                        # banner + fatal, exit 1: the file runs

mkdir -p ~/.local/bin && mv ./open-king ~/.local/bin/open-king
chmod +x ~/.local/bin/open-king

The archive holds the executable and nothing else, so it runs from wherever it was unzipped. /usr/local/bin is the alternative install location and needs sudo mv ./open-king /usr/local/bin/open-king.

macOS, Intel (x86_64)

The same sequence with the other asset name.

mkdir -p ~/open-king-dl && cd ~/open-king-dl
BASE=https://github.com/Broccolito/open-king/releases/download/v0.1.1

curl -LO "$BASE/open-king-macos-x86_64.zip"
curl -LO "$BASE/SHA256SUMS.txt"

shasum -a 256 -c SHA256SUMS.txt --ignore-missing
unzip open-king-macos-x86_64.zip

mkdir -p ~/.local/bin && mv ./open-king ~/.local/bin/open-king
chmod +x ~/.local/bin/open-king

Unverified

The Intel binary was not executed. The documenting machine is Apple silicon, so the x86_64 archive was downloaded and listed rather than run. The arm64 build of the same source was run there.

macOS signing and notarization

Both macOS builds are signed with a Developer ID certificate, under the hardened runtime and with a secure timestamp, and are notarized by Apple. Apple returned Accepted with status Ready for distribution, and issued a ticket against each binary's code hash. The binaries run straight out of the archive: no Gatekeeper prompt, and no xattr -d com.apple.quarantine step, whether the archive arrived through a browser or through curl.

A bare command-line executable cannot carry a stapled ticket, because Apple staples tickets to app bundles, disk images and installer packages rather than to loose Mach-O files. The first run therefore checks the ticket with Apple over the network, which is ordinary for a notarized command-line tool. The check is Gatekeeper's, not the program's: open-king opens no sockets of its own.

mkdir -p ~/open-king-dl && cd ~/open-king-dl

The target is x86_64-unknown-linux-gnu, so a glibc system is required.

Windows x86_64

Download open-king-windows-x86_64.zip and SHA256SUMS.txt from the release page, or with gh. The zip holds one file, open-king.exe, at the archive root. 

mkdir $HOME\open-king-dl; cd $HOME\open-king-dl
gh release download v0.1.1 --repo Broccolito/open-king `
  --pattern 'open-king-windows-x86_64.zip' --pattern 'SHA256SUMS.txt' --clobber

(Get-FileHash open-king-windows-x86_64.zip -Algorithm SHA256).Hash.ToLower()
# compare against the matching line in SHA256SUMS.txt

Expand-Archive open-king-windows-x86_64.zip -DestinationPath .\open-king-bin -Force
mkdir $HOME\bin -Force
Move-Item .\open-king-bin\open-king.exe $HOME\bin\open-king.exe -Force

Signing and notarization cover the two macOS builds. The Windows executable is not signed, so SmartScreen may warn about it; the Get-FileHash comparison above is what establishes that the file is the released build.

Unverified

No Windows host was available. The commands above follow from the archive layout the release workflow produces and from standard PowerShell usage; they were not executed.

Build from source

Install Rust

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
rustc --version

To build against the declared floor rather than your default toolchain:

rustup toolchain install 1.75
cargo +1.75 build --release

Clone and build

The repository is public, so an unauthenticated HTTPS clone works.

git clone https://github.com/Broccolito/open-king
cd open-king
cargo build --release

gh repo clone Broccolito/open-king and git clone git@github.com:Broccolito/open-king.git reach the same tree.

The workspace has three crates, open-king-io, open-king-core and open-king-cli. The binary is declared by open-king-cli, is named open-king, and lands at target/release/open-king. The release profile is opt-level = 3, thin LTO, one codegen unit, and panic = "abort".

To build only the CLI, which is what the release workflow does per target:

cargo build --release -p open-king-cli

Verify the install

Smoke test

Run the binary with no arguments.

open-king

It exits 1 and prints the banner plus a fatal block, because no input fileset was named. That is the expected result, and it is the cheapest proof that the file on disk runs. Measured first lines: 

KING 2.3.2 - (c) 2010-2023 Wei-Min Chen

The following parameters are in effect:
                   Binary File :                 (-bname)

Additional Options
         Close Relative Inference : --related, --duplicate
...

and, near the end of the same output, with three citation lines after it:

FATAL ERROR - 
Genotype files are required. e.g.,
  king -b ex.bed --related

Which program is on your path

open-king prints the banner KING 2.3.2 - (c) 2010-2023 Wei-Min Chen, and it responds to --version, -v, --help and -h with that same banner. This is deliberate: the project targets drop-in stdout parity, and the banner is part of stdout. Each of those four flags prints the banner, then a WARNING block, then the Genotype files are required fatal, and exits 1. There is no flag that prints 0.1.0.

The wording inside that warning block splits on the number of dashes, which matters if you grep for it. Measured: --version and --help report Command line parameter --version is undefined, while -v and -h report Command line parameter -v (#1) ignored. The number is the argv position of the flag. A single-dash typo is never called undefined.

KING 2.3.2 is the version of the reference program open-king reimplements, and open-king prints it verbatim, so on a machine that has both, the banner does not tell you which of the two is on your path. Two things do:

  • The path you invoked. Run the binary by absolute path, or check command -v open-king first, so the transcript records which file ran.
  • The checksum. SHA256SUMS.txt covers the release archives, so verifying an archive against it pins the build that was unzipped from it. For a binary already on disk, record its own SHA-256 and compare against that.

Run the tests

Generate the genotype corpus first. The filesets are not committed, and a test in open-king-core opens tests/parity/golden/multifam.bed directly (report.rs, plink_entrypoint_matches_a_reference_row_without_text_roundtrip), so on a fresh clone cargo test fails until that file exists. Note the output directory: it is tests/parity/golden here, not the tests/parity/work/data the parity runner defaults to. 

python3 tests/parity/generate_corpus.py --outdir tests/parity/golden
cargo test --workspace

The suite is 355 tests. .github/workflows/ci.yml runs those two commands in that order on Linux, macOS and Windows for every push to main and every pull request, and runs the 480-case parity suite beside it on Linux.

Unverified

cargo test --workspace was not run while the source notes were written, because another process held the cargo build lock. The command and the generation step before it are read directly out of .github/workflows/release.yml, where they are the first gate in the release workflow.

Differential parity suite

The .bed, .bim and .fam filesets are not committed. .gitignore excludes /tests/parity/work/ and tests/parity/golden/**/*.{bed,bim,fam}. The generator is committed and is deterministic from a single seed, so everyone regenerates the same bytes. 

python3 tests/parity/generate_corpus.py --outdir tests/parity/work/data
python3 tests/parity/run_parity.py --impl ./target/release/open-king -q --baseline

Generation was measured at 4.2 s wall, exit 0, 13 datasets, 40 files totalling 10.3 MB. Two notes about where the data goes, both read out of tests/parity/run_parity.py:

  • The runner's default dataset directory is tests/parity/work/data (DEFAULT_DATA = PARITY_DIR / "work" / "data"), not tests/parity/golden. Generating into golden puts the filesets where the runner will not look unless you also pass --data tests/parity/golden.
  • Pre-generating is optional. ensure_inputs() checks the 13 datasets and runs the generator itself for any that are missing. Generating first makes the first run faster and the failure mode clearer.

--baseline with no argument defaults to tests/parity/BASELINE.txt, which records one line per case. That file currently holds 480 lines, all PASS. Measured, running the released v0.1.0 binary against the committed baseline: 

$ python3 tests/parity/run_parity.py --impl <open-king> -q --baseline \
    --data <corpus> --alt <alt>
[parity] 480 case(s), impl=/…/open-king, jobs=8

parity: 480 PASS, 0 FAIL, 480 total (2.3s wall, 876 output file(s) byte-compared, 8 diff-excluded)
baseline: MATCH (480 case(s) against BASELINE.txt)
$ echo $?
0

A correct result is exactly that: 0 FAIL on the summary line, baseline: MATCH on the next, exit status 0. The [parity] … progress line goes to stderr; the two result lines go to stdout. A mismatch prints baseline: MISMATCH against BASELINE.txt (N line(s) changed) followed by a unified diff, and exits 1. The suite fails in either direction: a case that newly passes is also a mismatch, resolved with --write-baseline plus a commit. The parity page covers what was compared and what is still open.

Each case runs in its own tempfile.mkdtemp() directory, so the suite does not write into your working directory. --impl is absolutized before use, so a relative path is fine.

Put it on PATH

Copy the binary into a directory that is already on PATH, or add a directory to PATH. The program reads no configuration and looks for nothing beside itself, so a bare copy is enough. 

mkdir -p ~/.local/bin
install -m 0755 target/release/open-king ~/.local/bin/open-king
export PATH="$HOME/.local/bin:$PATH"   # add to ~/.zshrc or ~/.bashrc to persist
open-king                              # banner + fatal, exit 1: the install is good

On Windows:

# this session only:
$env:Path = "$HOME\bin;$env:Path"
# persist:
[Environment]::SetEnvironmentVariable('Path', "$HOME\bin;$env:Path", 'User')

Copy rather than symlink into the target directory if you plan to rebuild while a run is in flight.

Setup for a coding agent

Every claim in this section was measured by running the binary, except where marked otherwise. The behaviours below are the ones that cost an unattended caller the most time when they are discovered late.

Resolving the binary

Both PATH and an absolute path work. An absolute path is the safer default for an agent: it is immune to a PATH that differs between the agent's shell and a login shell, and it makes the file in use explicit in the transcript. There is no wrapper script and no open-king subprocess lookup, so nothing else has to resolve the name. PATH is required if the agent hands the command to a tool that reconstructs the argv itself, or if the same recipe has to run on machines with different install locations.

Resolve once at the top of a session and reuse:

OPEN_KING=$(command -v open-king || echo "$HOME/.local/bin/open-king")
[ -x "$OPEN_KING" ] || { echo "open-king not installed"; exit 127; }

Record the SHA-256 of the binary alongside it. The banner reports KING 2.3.2, the reimplemented reference's version, so it cannot identify the build. See which program is on your path.

Output lands in the working directory

This is the behaviour to plan around first. --prefix defaults to the literal string king and is applied by plain string concatenation, not by joining a stem to a directory. From crates/open-king-cli/src/analysis/mod.rs: 

pub fn out_path(opts: &Options, suffix: &str) -> String {
    format!("{}{suffix}", opts.string(Opt::Prefix))
}

Consequences, all measured:

Command, run in an empty directory Files created there
open-king -b …/multifam.bed --kinship king.kin, king.kin0
open-king -b …/multifam.bed --related --degree 2 --prefix demo demo.kin, demoallsegs.txt
open-king -b …/bigish.bed --related --degree 2 --prefix out/run_ out/run_.kin, out/run_.kin0, out/run_allsegs.txt

Note demoallsegs.txt, with no dot. The suffix carries its own separator, so --prefix demo gives both demo.kin and demoallsegs.txt. An agent must therefore do one of two things: change directory into a scratch directory before invoking open-king, or pass a --prefix with a directory component such as --prefix out/run_.

The directory named in a prefix must already exist. open-king does not create it. Measured: 

$ open-king -b trio.bed --kinship --prefix nodir/x
...
FATAL ERROR - 
Cannot open nodir/x$TMP$.ped to write.
$ echo $?
1

The check is a real write test, performed early, before the pedigree is parsed: open-king creates <prefix>$TMP$.ped, then removes it. A read-only directory fails it too. The code is crates/open-king-cli/src/load.rs::probe_tmp_ped. Because output names are a pure function of --prefix, two runs sharing a prefix in the same directory overwrite each other, including the transient <prefix>$TMP$.ped. Give each concurrent run its own directory or its own prefix.

Exit status

Two statuses are produced. 0 means the run completed. 1 means a fatal error: a FATAL ERROR block was printed and nothing further ran. Only fatal() in crates/open-king-cli/src/main.rs exits 1; every other termination is std::process::exit(0).

Command Exit
open-king (no arguments) 1
open-king --version / -v / --help / -h 1
open-king -b multifam.bed --kinship 0
open-king -b multifam.bed (no analysis requested) 0
open-king -b multifam.bed --kinship --bogus (undefined flag) 0
open-king -b /nope/missing.bed --kinship 1
open-king -b multifam.bed --pca (out of product scope) 1
open-king -b trio.bed --kinship --prefix nodir/x 1

The two bold rows are the traps.

  • An undefined flag does not fail the run. --bogus produces a WARNING block and the analysis proceeds to completion with exit 0. A typo in an agent-generated command line is silent unless you grep for it.
  • Requesting no analysis does not fail either. open-king -b file.bed loads the fileset, prints a notice, writes nothing, and exits 0. Checking the exit status alone reports success for a run that produced no results.

Unverified

The status of a Rust panic. The release profile sets panic = "abort", so a panic would terminate on SIGABRT, which a shell reports as 134, rather than exiting 1. No input was found that panics, so this was not observed.

Everything goes to stdout

Measured across every invocation in the source notes and again while writing this page, successful and fatal: stderr received 0 bytes in all cases. The FATAL ERROR block is written to stdout, not stderr. That is deliberate reference-console parity, stated in the module docs of main.rs: everything goes to stdout, the reference writes nothing to stderr, and neither does open-king. This is unusual enough to state plainly, because it breaks the ordinary assumption that diagnostics arrive on stderr.

  • Capturing only stderr captures nothing, ever.
  • cmd > log 2>&1 and cmd > log are equivalent here. Prefer the first anyway.
  • Diagnostics have to be recovered from the stdout log, keyed off the exit status.

Three byte-level details of that log, all measured with od -c:

  • The fatal marker line is exactly FATAL ERROR - , with a trailing space and no leading control character. grep '^FATAL ERROR' log matches.
  • The warning marker line is \aWARNING - , prefixed by a BEL byte (0x07). grep '^WARNING' log matches nothing. Use grep 'WARNING - ' unanchored.
  • Genotype loading progress is written as carriage-return-separated tokens (0%\r6%\r13%\r…) even when stdout is redirected to a file rather than a terminal. A line-oriented parser has to tolerate embedded \r.

Output files an agent can rely on

Not every declared output file is written on every run, and an existing file is not proof of a result.

  • .kin0 is written only when cross-family relatives were found. Measured: multifam with --related --degree 2 prints No close relatives are inferred. and produces demo.kin and demoallsegs.txt but no .kin0. bigish with the same flags produces all three.
  • An output file can legitimately be empty. Measured: open-king -b trio.bed --kinship writes a 0-byte king.kin and exits 0. This matches the captured reference goldens for the same command, which are also 0 bytes, so it is correct behaviour and not a failure.

Test with [ -s file ], not [ -f file ]. The output files page covers the columns of each file.

Property Evidence
No interactive prompt no stdin reference anywhere in crates/
No network access Cargo.lock holds the workspace's own three crates and twelve other packages: flate2, rayon-*, miniz_oxide, crc32fast, crossbeam-*, either, adler2, cfg-if, simd-adler32. No HTTP or socket crate, and no std::net reference in crates/

Worked example

An agent-shaped wrapper, run and verified in all three branches: success, flag-typo warning, and fatal input error. The warning branch was checked with both a --bogus and a -x typo, because the two produce different wording. 

#!/bin/sh
# Usage: open-king-run.sh <fileset.bed> <workdir>
set -eu
bed=$1
work=$2

mkdir -p "$work/out"
cd "$work"

status=0
open-king -b "$bed" --related --degree 2 --prefix out/run_ > run.log 2>&1 || status=$?

if [ "$status" -ne 0 ]; then
  echo "open-king failed (exit $status)"
  sed -n '/FATAL ERROR/,$p' run.log
  exit "$status"
fi

# A typo in a flag does not fail the run; it only warns. Note the unanchored pattern:
# the WARNING line carries a leading BEL byte. A --flag typo reads "is undefined"
# and a -f typo reads "(#N) ignored", so match both, and tolerate no match under set -e.
if grep -q 'WARNING - ' run.log; then
  echo "open-king warned about the command line:"
  grep -E 'is undefined|ignored' run.log || true
fi

# .kin0 is written only when cross-family relatives were found.
if [ -s out/run_.kin0 ]; then
  echo "cross-family pairs: $(( $(wc -l < out/run_.kin0) - 1 ))"
  awk -F'\t' 'NR > 1 && $14 == "FS" { print $1"/"$2, $3"/"$4, $10 }' out/run_.kin0
else
  echo "cross-family pairs: 0"
fi

.kin0 is tab separated with a header row and 14 columns. Field 10 is Kinship and field 14 is InfType, which the awk line above reads. Measured output on the bigish corpus fileset: 

$ ./open-king-run.sh /tmp/corpus/bigish.bed /tmp/w1
cross-family pairs: 26
BF01/B01_F BF02/B02_F 0.2885
BF13/B13_F BF14/B14_F 0.2959
BF25/B25_F BF26/B26_F 0.2504
$ echo $?
0

With --bogus inserted into the command line:

open-king warned about the command line:
Command line parameter --bogus is undefined
cross-family pairs: 26
...

With a missing input:

$ ./open-king-run.sh /nope/x.bed /tmp/w3
open-king failed (exit 1)
FATAL ERROR - 
Genotype file /nope/x.bed cannot be opened
$ echo $?
1

Checklist

Do Why
Change directory to a scratch directory, or use --prefix dir/stem output lands in the current working directory
Create the prefix directory first open-king will not; it exits 1
Branch on exit status: 0 or 1 only those two are produced
Also grep the log for WARNING - an undefined flag exits 0
Check that the expected output file exists and is non-empty a run with no analysis requested exits 0 and writes nothing, and a successful run can leave a 0-byte file
Read diagnostics from stdout stderr is always empty
Give concurrent runs separate directories or prefixes output names are a pure function of --prefix
